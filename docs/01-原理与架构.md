# 01 — 原理与架构

> 这篇是"讲明白"的核心。主人问"这是怎么做的"，从这里讲起。

## 封号的根因：环境不一致

账号被封，很少是"你用得太狠"，更多是**环境在风控眼里前后对不上**：

| 触发点 | 表现 |
|---|---|
| 出口是机房 IP | 服务器 IP 段被标记为数据中心，不像真实用户 |
| 出口老在变 | 今天这个 IP、明天那个 IP，会话环境断裂 |
| 代理挂掉偷偷回退 | 代理一断，流量切回服务器原始机房 IP，等于自己把环境变了 |
| 登录请求从本地发出 | 邮件里的图片、登录链接点开时由本地浏览器发请求，暴露真实环境 |
| 多账号 Cookie / 会话混淆 | 几个号在同一浏览器里轮换，登录态互相污染 |

这套方案的思路就是：**把所有会"露出真实环境"的环节，全部搬进一个固定的美国住宅网络里。**

## 整条链路

```text
本地电脑  →  美国 AWS 服务器  →  美国静态住宅 IP  →  Claude
(远程操作)    (登录/授权/使用全在这)   (固定出口)      (服务对象)
```

类比：在美国放了一台专门用 Claude 的电脑，你坐在自己电脑前操作它。Claude 看到的始终是一台"美国住宅网络里的正常电脑"，而不是一个东跳西跳的机房 IP。

## 三部分，缺一不可

1. **一台美国 AWS 服务器**——把使用环境整体搬过去。
2. **一个固定的美国静态住宅 IP**——给这台服务器一个真实、稳定的出口。注意是住宅代理的固定出口，**不是** AWS 控制台里的静态公网 IP（那是机房 IP，正是要躲开的东西）。
3. **断网保护（整套方案的命门）**——所有业务联网都必须走住宅代理；代理断开、超时或重启时，**宁可断网，也不许切回服务器原始 IP**。保留 SSH 管理通道，重启后保护策略仍生效。

## 为什么是这三部分，而不是别的

- **只换 IP 不够**：本地环境、登录请求、浏览器指纹还在原地，IP 干净了别的环节依然暴露。
- **只上服务器不够**：服务器默认出口是机房 IP，风控一眼识别。
- **不做断网保护等于没做**：代理总会有断的时候，那一刻回退到机房 IP，前面全白费。作者反复强调"宁可断网，也绝不换出口"。

## 多账号为什么能共用一台服务器一个出口

实测是单台服务器、同一个静态住宅 IP 跑 3 个 Pro 账号稳定。做法是：

- 每个账号一个**独立的 Chrome 用户配置文件**，隔离 Cookie 和登录态（注意：只隔离登录态，不为不同账号分配独立出口）。
- 用 tmux 建 `claude-a` / `claude-b` 切换入口：凭证各自独立保存，项目代码、CLAUDE.md、任务进度、交接记录**共享一份**。
- A 账号把进度和下一步写进共享交接文件，B 账号读文件接着干。

⚠️ 3 个账号稳定 ≠ 更多账号也安全，作者没测过上限。禁止多个会话同时改同一份代码。

## 记忆为什么要备份到 GitHub

账号万一被封，会话和记忆都在服务器上，可能一起没了。把 memory、readable、sessions、tools、工作空间代码、交接脚本定时备份到 GitHub，就算号被封，记忆还在，可以无缝迁到新账号。这是整套方案里**唯一没有副作用、纯赚**的一条——就算不做前面的，这条也建议做。

## 一句话总结

> 环境一致性是核心：固定出口 + 全链路搬到美国住宅网络 + 断网保护兜底。封号概率降低，但不归零。
